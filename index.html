Part I

Media & On-Disk Layout

How physical hardware physics shapes storage engine software. NAND flash erase-before-write constraints, slotted page formats, and columnar columnar vectors.

01 Storage Physics

Physical Storage Media: Flash SSDs, Blocks & Pages

Solid-state drives (SSDs) are built from NAND flash memory cells. Unlike spinning magnetic disks, flash storage has an asymmetric access constraint: data can be read and programmed (written) in 4KB to 16KB Pages, but pages cannot be overwritten in place. Instead, an entire Erase Block (typically 2MB to 8MB) must be erased to electrical charge 1s before any page can be reprogrammed.

This creates the Flash Translation Layer (FTL) and Write Amplification Factor (WAF): writing 1 byte of user data can trigger multiple background page copies during garbage collection.

02 Page Format

Slotted Page Architecture & Variable-Length Tuples

Modern relational storage engines (PostgreSQL, MySQL InnoDB, SQLite) organize data on disk in fixed-size blocks (typically 8KB or 16KB). Because rows can vary in length (strings, text, arrays), storage engines employ the Slotted Page Layout.

The page header grows from the top downwards, storing an array of slot pointers: each slot contains the byte offset and length of a tuple. Raw tuple data is written from the bottom of the page upwards. This decouples the physical memory address of a record from its logical RecordID (PageID, SlotIndex): tuples can be defragmented and shifted in-place without invalidating foreign keys or secondary indexes!

03 Access Patterns

Row-Oriented (NSM) vs. Columnar (PAX / Parquet) Storage

The N-ary Storage Model (NSM) stores all attributes of a single row contiguously on disk. This is optimal for OLTP transactions: fetching or inserting an entire row requires reading only a single disk block.

However, analytical queries (OLAP) typically scan billions of rows across only two or three columns (e.g. SELECT avg(price) FROM orders WHERE status = 'SHIPPED'). Reading full NSM rows wastes 90%+ of memory bandwidth loading unused columns. Partition Attributes Across (PAX) and columnar formats (Parquet, ORC, ClickHouse) store contiguous vectors of the same column, enabling 10x higher compression (Run-Length Encoding, Dictionary Encoding) and SIMD vectorized query execution.

04 Append-Only Logs

Log-Structured Append-Only Storage: The Bitcask Model

Bitcask (from Riak) represents the simplest high-performance key-value engine. All writes, updates, and deletes are appended sequentially to the active log file on disk. In-memory, Bitcask maintains a Keydir Hash Table mapping every active key to its exact file_id, value_size, value_pos.

Because all writes are purely sequential, Bitcask saturates disk write bandwidth with near-zero write amplification. Reads require exactly 1 disk seek directly to the offset. Background merge threads asynchronously compact stale and tombstoned entries into dense consolidated data files.

Part II

Indexes & Trees

The two fundamental pillars of database indexing: B+ Trees (read-optimized in-place updates) and Log-Structured Merge-Trees (write-optimized out-of-place appends).

05 B+ Tree Core

B+ Trees in Depth: Fanout, Balancing & Page Splits

The B+ Tree is a self-balancing N-ary tree where all user data is stored exclusively in leaf nodes. Interior nodes store only separator keys and child pointers, maximizing Fanout ($B \approx 100 \text{ to } 500$ children per page). With high fanout, a 4-level B+ tree can index billions of rows with only 3 to 4 page hops from root to leaf!

When an inserted key overflows a leaf page beyond its capacity $M$, the node undergoes a Page Split: the middle key is promoted to the parent interior node, and leaf siblings are linked via doubly linked pointers for ultra-fast sequential range scans.

06 B-Tree Concurrency

B-Tree Concurrency: Latch Crabbing & Optimistic Coupling

Databases distinguish between logical Locks (held by transactions for ACID isolation until commit) and physical Latches (held by threads for microseconds to prevent race conditions on page data structures). To traverse a B-tree concurrently without bottlenecking the root, engines use Latch Crabbing:

  • Acquire latch on parent node.
  • Acquire latch on child node.
  • Check if child is "safe" (will not split on insert, or will not merge on delete). If safe, immediately release latch on parent!
07 LSM Architecture

Log-Structured Merge-Trees: MemTable to SSTable

Introduced by O'Neil et al. (1996) and popularized by Bigtable, RocksDB, and Cassandra, the LSM-Tree trades read latency for near-unlimited write throughput. Writes are appended to a Write-Ahead Log (WAL) on disk for durability, then inserted into an in-memory sorted structure (the MemTable, typically a SkipList or Red-Black Tree).

When the MemTable reaches its threshold size (e.g. 64MB), it is frozen into an immutable MemTable and flushed sequentially to disk as an SSTable (Sorted String Table). Reads check the MemTable first, then consult Bloom Filters before probing SSTable disk files.

08 LSM Compaction

Compaction Strategies: Size-Tiered vs. Leveled

Because SSTables are immutable, updates and deletes create duplicate keys and tombstone records scattered across multiple disk files. Compaction is the background merge-sort process that unifies SSTables, discards superseded records, and bounds read amplification:

  • Size-Tiered Compaction (STCS): Waits for $N$ SSTables of similar size, then merges them into one larger SSTable. Low write amplification, but high temporary disk space overhead (up to 50% space amplification).
  • Leveled Compaction (LCS, RocksDB): Organizes SSTables into geometric levels (Level 0, Level 1, Level 2) where each level is $10\times$ larger. Within Level 1+, SSTable key ranges are strictly non-overlapping. Lower space amplification ($\approx 10\%$) and faster point lookups, but higher write amplification.
Part III

Buffer Management & OS I/O

How database engines manage memory, bypass kernel overhead, and guarantee that modified pages reach non-volatile storage safely.

09 Memory Management

Buffer Pool Management & Frame Tables

A database management system cannot afford to let the OS kernel handle memory paging. The DBMS knows query execution plans, index traversal order, and transaction commit boundaries—the OS kernel knows none of this. The DBMS therefore allocates an explicit Buffer Pool in user-space RAM.

The Buffer Pool is divided into fixed-size Frames. An in-memory Page Table maps on-disk PageID to in-memory FrameID. Every frame tracks two critical metadata flags: the Pin Count (number of concurrent queries actively reading or modifying the frame) and the Dirty Bit (indicating in-memory changes not yet written to disk). A page can never be evicted while its pin count is greater than zero!

10 Cache Eviction

Page Eviction Policies: LRU-K & 2Q

Classic Least Recently Used (LRU) suffers from a devastating vulnerability: Sequential Scan Pollution. When a single large query performs a full table scan across a 100GB table, it reads each page exactly once—wiping out the entire hot cache of frequently accessed index root pages!

Production DBMSs employ scan-resistant algorithms like LRU-K (O'Neil et al.) and 2Q (Johnson & Shasha). LRU-2 tracks the timestamp of the last two accesses to a page. A page accessed only once has a backward distance of $\infty$, ensuring one-time scan blocks are evicted immediately while hot items remain pinned in the active cache.

11 OS Kernel Bypass

Direct I/O (O_DIRECT) vs. Linux Page Cache & fsync

When an application calls standard write() on Linux, the kernel copies the data into the OS Page Cache and marks the kernel page dirty. This creates two fatal problems for databases: Double Buffering (wasting half of system RAM caching pages in both DBMS buffer pool and Linux page cache) and Uncontrolled Flush Stalls (when kernel pdflush / kswapd suddenly freezes I/O to flush gigabytes of dirty memory).

High-performance engines (PostgreSQL with Direct I/O, MySQL InnoDB with innodb_flush_method=O_DIRECT) bypass the OS page cache entirely using the O_DIRECT flag. Direct I/O enables DMA (Direct Memory Access) transfers straight from the DBMS buffer pool to the NVMe controller.

Part IV

Recovery & Transactions

The mathematical invariants of durability and isolation: Write-Ahead Logging, ARIES crash recovery, Two-Phase Locking, and MVCC snapshot isolation.

12 Durability Matrix

Write-Ahead Logging & The STEAL / NO-FORCE Matrix

How a DBMS manages dirty buffer frames in relation to transaction commit defines the STEAL vs. FORCE trade-off space:

  • STEAL: Can the buffer manager write a dirty page to disk before the modifying transaction commits? If YES (STEAL), the system needs UNDO logging in case the transaction aborts. If NO (NO-STEAL), uncommitted changes stay in RAM, severely limiting transaction sizes.
  • FORCE: Must all pages modified by a transaction be flushed to disk before the transaction commits? If YES (FORCE), commits require massive random disk writes. If NO (NO-FORCE), commits are instantaneous, but the system needs REDO logging to recover unwritten committed changes upon crash.

Modern production databases universally implement STEAL + NO-FORCE with Write-Ahead Logging (WAL).

13 Crash Recovery

ARIES Crash Recovery: Analysis, Redo & Undo

Invented by C. Mohan at IBM, ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) is the foundational crash-recovery algorithm used in enterprise DBMSs. Every log record carries a monotonically increasing Log Sequence Number (LSN), and every on-disk data page carries a pageLSN recording the last update applied to it.

Upon crash, ARIES executes three sequential phases:

  1. Analysis Phase: Scans the WAL forward from the last checkpoint to determine the state of the system at crash time, reconstructing the Dirty Page Table (DPT) and Transaction Table (TT).
  2. Redo Phase: "Repeats History" by scanning forward from the smallest RecLSN in the DPT and reapplying all logged updates (even those from uncommitted transactions) to restore the exact state at the crash point.
  3. Undo Phase: Scans backward reversing updates made by active loser transactions, writing Compensation Log Records (CLRs) to ensure recovery never cascades or undoes already undone work if a second crash occurs during recovery!
14 Concurrency Control

Concurrency Control: Two-Phase Locking (2PL) & Strict 2PL

To guarantee Serializability (ACID isolation), transactions must follow Two-Phase Locking (2PL). A transaction divides into two distinct phases: a Growing Phase (acquiring locks, no locks released) and a Shrinking Phase (releasing locks, no locks acquired).

However, basic 2PL suffers from Cascading Aborts: if Transaction 1 releases a lock early and Transaction 2 reads that uncommitted value, an abort of T1 forces an abort of T2. To prevent this, real databases use Strict 2PL (S2PL): all Exclusive (X) locks must be held until the transaction finishes (COMMIT or ABORT).

15 Multi-Version Concurrency

Multi-Version Concurrency Control (MVCC) & Tuple Visibility

Under lock-based concurrency, "readers block writers and writers block readers." Multi-Version Concurrency Control (MVCC) solves this fundamental bottleneck: readers never block writers, and writers never block readers!

In PostgreSQL and Oracle, updates do not modify tuples in place. Instead, the engine creates a new version of the row. Each tuple header stores two transaction identifiers: xmin (the transaction ID that created the tuple) and xmax (the transaction ID that deleted or superseded it). When a transaction reads under Snapshot Isolation, it consults its active transaction snapshot: a tuple is visible if and only if xmin ≤ Read_Snapshot and (xmax > Read_Snapshot or xmax == 0). Obsolete versions are later reclaimed by asynchronous background VACUUM workers.
